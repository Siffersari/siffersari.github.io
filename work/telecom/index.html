Telecom order systems — requirements to production

Requirements, design, delivery and production ownership across connected enterprise telecom platforms.

Delivery and production ownership across the order stack

React · TypeScript · APIs · Playwright · CI/CD

What I did

  • Clarified what was actually being asked before building — separating support questions from defects from genuine change requests, and sizing the real scope of a report rather than the reported one.
  • Contributed to high- and low-level designs, implementation plans and release documentation, naming the technical trade-offs, bottlenecks and single points of failure while a change could still be argued about.
  • Reverse-engineered unfamiliar deployments — including establishing which build was actually running before spending a day debugging what it was doing.
  • Traced behaviour across frontends, backends, APIs, repositories and connected platforms, to tell environment, configuration, data, integration and application failures apart.
  • Judged when to investigate, when to clarify, when to escalate and when to de-escalate, with both engineering and business stakeholders in the room.
  • Carried changes through SIT and UAT into production deployment, then stayed with them — monitoring, regression handling and the fixes that followed.
  • Built and maintained the browser-test architecture used across seven enterprise CRM modules: page objects, deterministic waits, environment-aware runs, and test data managed as infrastructure. One example of what it caught: a race condition between concurrent orders that only appeared under real timing.
  • Used AI coding tools daily to hold that pace, reviewing every generated change as my own before it shipped.

What this provesI can own a change end to end in a system I did not write — from an unclear request, through design and release, to being the person still responsible after it ships.
